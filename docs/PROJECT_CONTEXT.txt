PURPOSE AND STACK
Laboratory management of referred isolates, patient/specimen data, antimicrobial
susceptibility testing (AST), review and release of reports, whole genome
sequencing (WGS), concordance, and turnaround time (TAT).
Server-rendered Django application with shared templates and Argon/Bootstrap
assets. requirements.txt pins Django 5.0.12; Docker targets Python 3.12.2.
Active settings select PostgreSQL. A db.sqlite3 file also exists, but is not
the configured database backend. Pandas/OpenPyXL support spreadsheets;
ReportLab/xhtml2pdf/pypdf support reporting. Gunicorn, WhiteNoise, Nginx and
Docker Compose are included. Root package.json has no build/test scripts.

CURRENT CODE WORKFLOW (RECHECK WHEN EDITING)
1. Secretariat creates a ReferralReceipt for a courier batch, with permanent
   receipt UUID/QR and receiving history; endorses it to the laboratory.
2. Receipt status proceeds received -> endorsed -> lab_received through explicit
   authorized actions. A QR scan is navigation, not a custody mutation.
3. LaboratoryReceiving records acceptance/rejection decisions;
   LaboratoryAccession stores ranges, linked batches and derived exact accessions.
   LaboratoryOrganismCount stores range-level organism inventory.
4. Current isolate workflow puts Main Laboratory ID BEFORE revival:
   id_pending -> id_testing -> id_returned -> revival_queued ->
   revival_in_progress -> revived -> id_reviewed -> ready_for_biobank -> biobanked.
   Revival failure/non-viable and retry paths also exist.
   laboratory_workflow.py uses atomic transactions and row locks for transitions.
   Identification/cassette return is required across the range before queueing
   revival. Printing and uploads must not imply completed physical workflow.
5. ID review, approved organism identity/code, harvest and lyophilization dates,
   then validated storage position gate biobanking. Isolate stickers use the exact
   accession and QR; these differ from courier receipt labels.
6. DMU raw/final data follows batch and verification workflows. Verification
   includes raw verification, final encoding/verification/printing, manager/head
   review, corrections, withdrawal, signing and release. Check actual transition
   functions rather than assuming every named status is a linear mandatory step.
   Raw edits after copying to Final can require Final review flags.

PERMISSIONS AND INTEGRITY
- Central role normalization/flags: apps/home/permissions.py.
  Roles: Admin, Secretariat, LAB Encoder, Laboratory Staff, DMU Encoder,
  Checker, Verifier, Manager; legacy role aliases exist; roles can be combined.
- Roles come from Django groups and ARSP staff profile. Current code treats
  is_staff and is_superuser as Admin authority; preserve/assess this explicitly
  if changing authorization. Navigation flags alone do not authorize an action.
- Receiving permissions: apps/receiving/permissions.py. LAB Encoder handles
  laboratory receipt/review; Laboratory Staff handles Main Laboratory ID;
  both can use permitted biobank functions; Admin spans operational roles.
- Current receipt deletion differs from older planning notes: Secretariat can
  delete eligible pre-laboratory-custody receipts; Admin can also remove an empty
  laboratory-received receipt. Any accession ranges block deletion for all roles.
  Review services.py and typed-confirmation POST view together before changing.
- WGS projects retain original accessions and survive Final deletion; automatic
  reconciliation must not overwrite an existing project or ambiguous match.
- home/signals.py and home_final/signals.py implement derived AST interpretation,
  emerging/classification/report behavior and deletion-related side effects.
  Review these when changing model saves, imports, bulk operations or deletion.
- Keep schema changes paired with migrations. Do not reset or migrate a live
  database just to orient yourself. Avoid exposing .env or patient/upload content.
